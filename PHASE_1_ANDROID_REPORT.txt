============================================================
1. SCOPE OF PHASE 1
============================================================
Convert the existing React/TypeScript Smart Alarm simulator into a real,
buildable, installable Android application covering:
  - Room-backed persistence (Alarm + AlarmOccurrence entities)
  - Occurrence-based scheduling (Alarm = rule, AlarmOccurrence = one
    concrete scheduled instance), via a real android.app.AlarmManager
    abstraction (AlarmScheduler / AndroidAlarmScheduler)
  - Local-clock-time-only recurrence math (ONE_TIME, WEEKLY) - no
    geofencing (Phase 2) and no cross-timezone behavior (Phase 3)
  - Full-screen ringing UI + notification with Android 13+
    POST_NOTIFICATIONS runtime permission handling
  - Boot recovery (RescheduleAllUseCase via BootReceiver)
  - Adaptive Compose UI (phone list/edit navigation + wide-screen
    two-pane layout)
  - Real JVM unit tests (12 test files, no Robolectric/instrumentation
    required for the domain/use-case layer)

Explicitly NOT in Phase 1 (per the agreed staged plan): geofencing/location
(Phase 2), timezone-shift-aware alarms (Phase 3), and later features
(Phase 4/5). None of that was started.

3. KNOWN LIMITATIONS / HONEST CAVEATS
============================================================
1. Compose `Modifier.weight()` is unusable under the current pinned
   toolchain (Kotlin 2.4.10 + Compose UI 1.12.0 / compose-bom
   2026.08.00): calling it fails compilation with "Cannot access 'val
   RowColumnParentData?.weight: Float': it is internal in file". This
   was verified to be a real, reproducible compiler/library binary
   incompatibility (ruled out: stale build cache, dependency-version
   conflicts, and a Kotlin 2.4.20-RC2 diagnostic bump - all failed
   identically). Worked around in 4 files (SmartAlarmNavHost.kt,
   AlarmListScreen.kt, AlarmEditScreen.kt, AlarmRingingScreen.kt) using
   `fillMaxWidth(fraction)` + directional padding, or `widthIn(max=...)`
   for one asymmetric case. Functionally equivalent for all normal
   content; the one cosmetic edge case is a very long alarm name in the
   list row, which is capped at 240dp width instead of flexibly sharing
   space with the toggle switch - a minor wrapping/truncation difference,
   not a functional bug.

2. Notification-permission-revoked gap: if a user revokes
   POST_NOTIFICATIONS from system settings after granting it once, the
   ringing notification (and with it the full-screen intent that is
   currently the ONLY path to launching the ringing screen - see
   AlarmReceiver.kt) is skipped entirely for that occurrence. There is no
   fallback (e.g. directly starting the ringing Activity from the
   receiver) yet. This is called out in-line in NotificationHelper.kt
   and is left for a later phase, since a fallback needs its own design
   work around Android's background-activity-launch restrictions, which
   differ by OS version.

3. Release APK is unsigned. No release keystore/signing config exists.
   Fine for Phase 1 (debug-build verification only); will need real
   signing setup before any real-world release distribution.

4. compileSdk is 37 while targetSdk is kept at 36 (compileSdk 37 is
   required by the resolved Compose 1.12.0 AARs' metadata check; this is
   a normal, supported configuration - compileSdk may exceed targetSdk).

4. TWO REAL PRODUCTION BUGS FOUND AND FIXED DURING TESTING
============================================================
(found via failing unit tests, not by inspection - see commit 499eb17)

1. AlarmFireUseCase never told the scheduler abstraction that a fired
   occurrence's AlarmManager entry was consumed - fixed by adding
   `coordinator.cancelScheduledEntry(occurrence.id)` right after the
   occurrence is marked FIRED.

2. OccurrenceCalculator.nextWeeklyOccurrence searched only `dayOffset in
   0..6` for the next matching day-of-week. When "today" is itself the
   only target day and its time has already passed, no offset in 0..6
   can match again - only exactly one week later (offset 7) can. Fixed
   by extending the loop to `0..7`. Re-verified against all existing
   OccurrenceCalculatorTest cases - no regression.

A third failure was a test-fixture bug, not a production bug: two boot-
recovery tests computed a hardcoded "boot time" as a fixed offset from
`now`, which silently stopped representing "device was off through the
alarm time" once the underlying occurrence date changed. Fixed by
deriving the boot time from the occurrence's own scheduled time instead.
