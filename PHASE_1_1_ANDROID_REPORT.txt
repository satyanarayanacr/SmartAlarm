============================================================
1. SCOPE OF PHASE 1.1
============================================================
This is an incremental addition on top of the already-verified Phase 1
Android app. Nothing about Phase 1 was restarted, rewritten, or removed.

Implemented in this phase:
  - A user-configurable daily "confirmation" check (default 9:00 PM) that
    looks at tomorrow's WEEKLY-recurring alarm occurrences and lets the
    user KEEP or SKIP each one for tomorrow only, without touching the
    recurring rule itself.
  - A notification ("Tomorrow's alarms") with Keep All / Review actions.
  - A review screen listing every WEEKLY alarm occurrence scheduled for
    tomorrow, with per-alarm checkboxes and Keep Selected / Skip Selected
    / (Keep All / Skip All) actions.
  - A new persisted global setting (enabled + confirmation time),
    editable from a new Settings screen reachable from the alarm list.
  - A new terminal occurrence state, SKIPPED, that cancels just that one
    occurrence's AlarmManager entry while leaving the parent Alarm and
    all other occurrences untouched.
  - Reboot recovery extended so the daily confirmation event is always
    re-armed, and SKIPPED occurrences are never resurrected.
  - A non-destructive Room migration (schema version 1 -> 2) adding one
    new table. No changes to the existing alarms / alarm_occurrences
    tables.

Explicitly NOT in this phase (per the Phase 1.1 spec): Phase 2
(location/geofencing), Phase 3 (timezone-change behavior), and any
Future-phase feature (email, calendar, YouTube alarm sounds, AI, cloud
sync, multi-device sync). None of that was started or touched.

============================================================
2. IMPLEMENTATION SUMMARY
============================================================
The existing Alarm -> AlarmOccurrence -> AlarmManager model from Phase 1
was extended rather than replaced. The confirmation feature is built as
its own small vertical slice (settings, use cases, a dedicated scheduler,
a dedicated receiver, dedicated UI) that reads and writes the existing
occurrence data rather than introducing a parallel scheduling path.

Key design decisions:
  - Only one new occurrence status was added (SKIPPED). "Keep" needed no
    new state: a SCHEDULED occurrence that is kept is simply left alone,
    which also naturally implements the required "no response -> keep"
    default (doing nothing is exactly the keep behavior).
  - The daily confirmation event uses a single, fixed AlarmManager
    request code (not one per alarm) registered against its own
    BroadcastReceiver (ConfirmationReceiver), because there is exactly
    one confirmation event per day, independent of how many alarms
    exist. This is the same FLAG_UPDATE_CURRENT idempotency pattern
    Phase 1 already uses per-occurrence, just simplified to a single id.
  - Confirmation scheduling is fully idempotent and stateless beyond the
    persisted settings: it is always recomputed from
    (current settings, current time), never from a separately stored
    "next trigger" value. This means reboot recovery and app-launch
    recovery can both just call the same "reschedule" use case
    unconditionally, with no separate restore-only code path to keep in
    sync.
  - Skipping an occurrence that belongs to a WEEKLY alarm immediately
    computes and schedules the alarm's next occurrence, anchored to the
    skipped occurrence's own scheduled time (not to "now"). This matters
    because the confirmation fires the evening before the alarm time
    (e.g. 9 PM the night before a 7 AM alarm) - anchoring to "now" would
    find the same still-in-the-future occurrence again instead of
    advancing to the following week.

3. CONFIRMATION WORKFLOW
============================================================
Daily (if enabled in settings):
  1. At the configured confirmation time (default 9:00 PM), the
     ConfirmationReceiver fires via a real exact AlarmManager alarm.
  2. It looks up every SCHEDULED AlarmOccurrence whose time falls within
     tomorrow (the calendar day after the device's current local date),
     restricted to alarms whose repeatType is WEEKLY. ONE_TIME alarms are
     never included.
  3. If that list is non-empty, it shows the "Tomorrow's alarms"
     notification with a count and two actions: Keep All, Review.
  4. It then re-arms itself for the following day's confirmation time
     (idempotent - see section 2).
  5. If the user does nothing: every occurrence stays SCHEDULED and rings
     normally. No automatic skipping ever happens.
  6. If the user taps Keep All: the notification is dismissed; no
     occurrence state changes (Keep is always a no-op, per section 2).
  7. If the user taps Review: the app opens directly to a review screen
     listing each tomorrow-WEEKLY occurrence with a checkbox (all checked
     by default) and four actions: Keep All, Skip All, Keep Selected
     (acts on checked items), Skip Selected (acts on checked items).
  8. Skipping an occurrence: cancels that occurrence's own AlarmManager
     entry, marks it SKIPPED, and (because its alarm is WEEKLY and still
     enabled) immediately schedules that alarm's next real occurrence for
     the following matching day. The parent Alarm is never disabled and
     no other occurrence is touched.
  9. Keeping an occurrence: no state change; it remains SCHEDULED and
     will ring at its normal time.

Race conditions handled (spec section 12):
  - Skip processed before the occurrence fires: proceeds as above.
  - Occurrence has already fired (or is not SCHEDULED for any other
    reason - MISSED, already SKIPPED, DISMISSED, SNOOZED, unknown id) by
    the time a keep/skip decision is processed: the use case returns the
    occurrence unchanged and takes no action. This also directly covers
    "user presses Skip twice" and "notification delivered twice" -
    both are idempotent no-ops on the second call, since after the first
    call the occurrence is no longer SCHEDULED.

============================================================
4. DATABASE CHANGES
============================================================
Room schema version bumped 1 -> 2. One new table added; the existing
`alarms` and `alarm_occurrences` tables are unchanged.

New table: confirmation_settings (singleton row, fixed id = 1)
  - id            INTEGER  PRIMARY KEY (always 1)
  - isEnabled     INTEGER  (0/1)
  - hour          INTEGER  (0-23)
  - minute        INTEGER  (0-59)
  - updatedAt     INTEGER  (epoch millis)

No column was added to, removed from, or retyped on any existing table.
The new OccurrenceStatus.SKIPPED value lives in the existing
alarm_occurrences.status TEXT column and required no schema change.

============================================================
5. SCHEDULER CHANGES
============================================================
- New ConfirmationScheduler interface + AndroidConfirmationScheduler
  implementation, deliberately separate from the existing
  AlarmScheduler/AndroidAlarmScheduler used for per-occurrence alarms
  (not a second incompatible mechanism - it uses the same AlarmManager
  exact-alarm APIs and the same exact-alarm permission check pattern,
  just scoped to a single global event instead of one per occurrence).
- AlarmSchedulingCoordinator.scheduleNextOccurrence gained a new,
  optional, backward-compatible `fromInstant` parameter (defaults to the
  existing "now" behavior, so every Phase 1 call site is unaffected)
  used only by the skip flow to anchor next-occurrence math to the
  skipped occurrence's own time rather than the confirmation-firing time.

============================================================
6. NOTIFICATION CHANGES
============================================================
- New notification channel (separate from the existing ringing channel)
  for the daily confirmation notification, IMPORTANCE_DEFAULT.
- New notification: title "Tomorrow's alarms", body states the count of
  alarms scheduled for tomorrow, actions Keep All and Review.
- Tapping Review opens MainActivity directly onto the review screen.
- Tapping Keep All dismisses the notification only; no data changes.
- The exact same inline permission-check pattern already proven (by a
  real Phase 1 build) to satisfy Android Lint's MissingPermission check
  was reused verbatim for this new notification call.

============================================================
7. UI CHANGES
============================================================
- Alarm list screen: added a "Settings" action in the top bar.
- New Settings screen: enable/disable switch for daily confirmation, plus
  a time picker for the confirmation time (shown only while enabled).
  Uses the project's established fillMaxWidth/widthIn layout approach
  rather than Compose's weight() modifiers, consistent with the existing
  Phase 1 workaround for the weight() binary-incompatibility issue
  documented during Phase 1.
- New Review screen: one row per tomorrow's WEEKLY occurrence with a
  checkbox (checked = "include in whichever action I press next"),
  showing the alarm's name and time, with Keep All / Skip All / Keep
  Selected / Skip Selected actions.
- Both new screens participate in the existing adaptive two-pane wide
  layout (tablet/landscape) the same way the existing alarm editor does,
  and fall back to full-screen navigation on compact layouts. No separate
  phone/tablet implementations were created.

19. KNOWN LIMITATIONS
============================================================
- Not yet build-verified (see sections 14-18) - this is the most
  important open item.
- The confirmation notification's "Review" action opens the app to the
  review screen; if notification permission (Android 13+
  POST_NOTIFICATIONS) is denied, no confirmation notification can be
  shown at all. Per spec section 17, this is treated as: no crash, no
  occurrence is silently modified, lack of permission is never treated
  as the user choosing SKIP, and every occurrence stays scheduled and
  will still ring normally. This mirrors the exact same limitation
  already present and documented for Phase 1's ringing notification -
  it has not been separately "solved" beyond that existing fallback
  behavior, since the spec does not ask for anything beyond it.
  A user who denies notification permission entirely will not see daily
  confirmation prompts, but will also never have an alarm silently
  skipped as a result - alarms simply ring as normal.
  a general settings/manual path to review or manage upcoming
  occurrences is only available through the Settings/Review screens
  described in section 7, both of which are reachable at any time, not
  only from the notification.
- Only JVM unit tests were written (matching the project's existing
  Phase 1 testing approach, which also has no
  Robolectric/instrumentation tests). No instrumented or Compose UI
  tests were added for the new screens; the spec allows this
  ("Add instrumented/UI tests where practical") and treats manual device
  testing (section 20) as the primary verification for UI behavior.
- The version-2 Room schema JSON snapshot (app/schemas) has not been
  generated yet, since it is produced by the Kotlin/KAPT compiler at
  build time and no build has run in this sandbox.
